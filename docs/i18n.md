# Internationalization (i18n)

Brambit is written in English and serves people in their own language. This page
is the contract for every change that touches text. It follows the same pattern
as other open-source agents, such as
[Hermes](https://github.com/NousResearch/hermes-agent): code, prompts and logs in
English; only the text a person reads in the product is translated, through
catalogs with stable keys.

> **Status:** this is the target design. The migration is in progress (see
> [Migration](#migration)). New text follows this page from now on.

## Who reads the text decides what happens to it

| Reader | Examples | Language |
| --- | --- | --- |
| The person using the product | screens, error messages shown to them, confirmation cards, emails, chat notices | **Translated**, through the catalogs on this page |
| The model | system prompt, tool descriptions, tool results | **English only, never translated** |
| Developers and operators | code, comments, logs, internal errors, tests, docs | **English only, never translated** |

The model replies in the person's language because the platform tells it which
language to use on every turn and checks the output (`web/locale.mjs`,
`web/freio-idioma.mjs`). Translating prompts or tool text changes model
behavior, so it is never part of an i18n change.

## Languages and fallback

- Languages are identified with [BCP 47](https://www.rfc-editor.org/info/bcp47)
  tags: `en`, `pt-BR`, `es`.
- **English (`en`) is the source language.** Every key exists in `en` first.
- Missing text falls back along the chain `pt-BR -> pt -> en`, and then to the
  key itself. A missing translation never breaks a page or a reply; CI reports it
  (see [Checks](#checks)).

## How the language is chosen

The language is resolved once per request or turn, in this order:

1. the language the person saved in their settings;
2. the language of the channel, when the channel reports one;
3. the browser's `Accept-Language`, used only as a first guess before a choice is
   saved ([W3C](https://www.w3.org/International/questions/qa-accept-lang-locales));
4. the instance default: `BRAMBIT_DEFAULT_LANGUAGE` (one of the supported tags),
   English when unset.

Texts not yet moved to the catalogs are written in Portuguese
(`LEGACY_TEXT_LANGUAGE` in `web/locale.mjs`). That is the language of those
literals, not a default: an instance with no setting speaks English and shows
them translated where a translation exists.

## Catalogs

Catalogs are JSON files, one per language, named after the tag (`en.json`,
`pt-BR.json`) and nested by key segment. They are resolved in layers (top wins):

1. plugin catalogs (the folders in the plugin's `locales` field, see
   `web/plugins.mjs`);
2. the instance overlay (the folder in `BRAMBIT_LOCALES_DIR`; `npm run brambit`
   uses `<data dir>/locales`), so an operator can adjust wording without
   forking;
3. the core catalogs (`web/locales/<lang>.json`);
4. the same chain for the fallback languages, down to `en`;
5. the key itself.

Every layer may be partial. The code is in `web/i18n.mjs`, built on
[i18next](https://www.i18next.com/).

## Keys

- Keys are **stable identifiers, never the sentence itself**: `confirm.delete_event.title`,
  not `"Delete this event?"`. Changing the English text must not invalidate the
  translations.
- Shape: `area.subject.detail`, lowercase `snake_case` segments. The first
  segment is the area (`confirm`, `routines`, `settings`, `errors`...).
- Name a key after its meaning, not its position on screen (`settings.save`, not
  `sidebar.button_3`).
- One key per meaning. Two places that happen to share the same English text but
  mean different things get two keys.
- When the meaning of a text changes, create a new key instead of editing the
  English text under the old one.

## Variables and plurals

- Variables use named placeholders: `"Couldn't rename it ({reason})"`. Never
  build a sentence by joining translated fragments; word order changes between
  languages. An optional clause (`" with the subject {subject}"`) is its own
  key and fills a placeholder of the sentence, so the sentence decides where it
  goes; the code passes an empty value when the clause is absent.
- Plurals use the [CLDR](https://cldr.unicode.org/index/cldr-spec/plural-rules)
  categories as key suffixes, and the form is picked from `count` with the
  language's own rules (`Intl.PluralRules`), never with `count === 1` in code:

  ```json
  { "items_one": "{count} item", "items_other": "{count} items" }
  ```

  Languages with more forms add them (`_zero`, `_two`, `_few`, `_many`).
- Translations are plain text: variables are not HTML-escaped. Code that puts
  a translated text into HTML escapes it there, like any other text.

## Dates, numbers, money and time

These follow the person, not the server:

- format dates and numbers with `Intl` and the resolved language, never with a
  fixed locale such as `toLocaleString('pt-BR')`;
- show times in the person's time zone (`users.timezone`), never a fixed one;
  when the person has none, use `defaultTimezone()` from `web/locale.mjs`
  (`BRAMBIT_DEFAULT_TIMEZONE`, else the machine's time zone);
- format money with `Intl.NumberFormat` and the currency of the amount.

## Plugins

A plugin ships its own catalogs, with its new keys under its own first segment
(the plugin name), so they never collide with the core. A plugin may also
replace a core text on purpose (same key) or ship a language the core does not
have. Check a plugin's catalogs with `node test-support/i18n-guard.mjs <folder>`.

## Pages

The HTML pages in `web/public` mark what a person reads, and the server fills
it from the catalogs in the person's language before sending the page
(`web/page-i18n.mjs`):

```html
<h1 data-i18n="usage_page.title">Usage &amp; cost</h1>
<input data-i18n-placeholder="usage_page.user_all" placeholder="all">
<p data-i18n="runner_page.lead">Let your assistant run commands on <b>your</b> machine.</p>
```

- `data-i18n="key"` replaces the element's content; `data-i18n-<attribute>`
  replaces that attribute (`placeholder`, `title`, `alt`, `aria-label`...).
- The English written in the page is the source for whoever reads the HTML;
  what is served comes from the catalogs.
- Child tags stay in the page and the catalog text places them by number, on
  each level, so a sentence is never cut into pieces: `"Let ... on <0>your</0>
  machine."` wraps "your" in the first child (`<b>`, with its attributes), and
  `<1/>` puts the second child back as it is (a command, an icon). The text is
  escaped: a catalog cannot add markup, only move the page's own.
- `{brand}` is filled by the server.
- A name that stays the same in every language (the brand, a language's own
  name in a language picker, a service like WhatsApp) gets the standard
  `translate="no"` attribute instead of a key; the check skips it, and
  browser translators leave it alone too.
- Text built by the page's script: an empty
  `<script type="application/json" data-i18n-texts="<area>"></script>` receives
  the `<area>.*` texts, and `/page-texts.js` gives the script
  `pageText('key', {name: value})`, with plurals when `count` is passed. Markup
  the script used to build goes in a `<template>` with marks instead.
  A script that still builds markup in strings (the main screen,
  `index_script.*`) uses `txHtml('key', {name: markup})`: the catalog text is
  escaped and each `{name}` receives markup the script built, so the catalog
  never adds tags and data passed in is escaped by the caller.

## Screens built in the browser

A page module that builds its own text (the onboarding wizard, the routines list) fetches its
area once, in the page's language: `GET /api/texts/<area>?lang=<tag>` answers
`{key: text}` for the `<area>.*` keys, with the same layers and fallback as the
server (`web/screen-texts.mjs`). To serve a new area, add it to `SCREEN_AREAS`.

## Adding a language

1. Copy `web/locales/en.json` to `web/locales/<tag>.json` and translate the values.
2. Add the tag to the list of supported languages.
3. Run the checks below.

No code changes are needed.

## Checks

`test-support/i18n-guard.mjs` (CI) fails when:

- a catalog has a key that `en` does not have;
- a translation uses placeholders different from the `en` text;
- user-facing text is written directly in code instead of through a key (added
  as each area is migrated).

`test-support/page-i18n-guard.mjs` (CI) fails when a page in `web/public`:

- marks a key that `en` does not have;
- has a catalog text, in any language, that names a child tag the element does
  not have;
- shows text that is neither marked nor in `test-support/legacy-page-texts.json`,
  the texts still on the old catalogs. That list may only shrink.

A key missing from a non-English catalog is reported, not fatal; it falls back to
English.

## Migration

The core still carries mechanisms from before this design. They are keyed by the
Portuguese text and will be moved to the catalogs above one at a time, keeping
the Portuguese output identical:

- site pages (`web/site-i18n.mjs`, `web/site-textos/`): `usage.html`, `runner.html`
  and `atendimento.html` are migrated, `index.html` is next. Both formats work
  meanwhile (the marks first, then the old catalogs); new text goes in the
  catalogs with a mark. When a page migrates, run
  `node test-support/page-i18n-guard.mjs --write` to drop its texts from the
  list.

Server messages are migrated: the core replies with `server.*` keys. The onboarding screens and the routines list are too (`onboarding.*`,
`routines.*`). The
confirmation card is migrated too (`confirm.*`, built in
`web/confirm-sentences.mjs`). A plugin's
`textosServidor` (keyed by the Portuguese sentence) still works, but new text
goes in its `locales`.

Until an area is migrated, keep its current key and add the translations, as
`AGENTS.md` says.
