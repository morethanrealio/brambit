# Internationalization (i18n)

Brambit is written in English and serves people in their own language. This page
is the contract for every change that touches text. It follows the same pattern
as other open-source agents, such as
[Hermes](https://github.com/NousResearch/hermes-agent): code, prompts and logs in
English; only the text a person reads in the product is translated, through
catalogs with stable keys.

> **Status:** this is the target design. The migration is in progress (see
> [Migration](#migration)). New text follows this page from now on.

## Who reads the text decides what happens to it

| Reader | Examples | Language |
| --- | --- | --- |
| The person using the product | screens, error messages shown to them, confirmation cards, emails, chat notices | **Translated**, through the catalogs on this page |
| The model | system prompt, tool descriptions, tool results | **English only, never translated** |
| Developers and operators | code, comments, logs, internal errors, tests, docs | **English only, never translated** |

The model replies in the person's language because the platform tells it which
language to use on every turn and checks the output (`web/locale.mjs`,
`web/freio-idioma.mjs`). Translating prompts or tool text changes model
behavior, so it is never part of an i18n change.

## Languages and fallback

- Languages are identified with [BCP 47](https://www.rfc-editor.org/info/bcp47)
  tags: `en`, `pt-BR`, `es`.
- **English (`en`) is the source language.** Every key exists in `en` first.
- Missing text falls back along the chain `pt-BR -> pt -> en`, and then to the
  key itself. A missing translation never breaks a page or a reply; CI reports it
  (see [Checks](#checks)).

## How the language is chosen

The language is resolved once per request or turn, in this order:

1. the language the person saved in their settings;
2. the language of the channel, when the channel reports one;
3. the browser's `Accept-Language`, used only as a first guess before a choice is
   saved ([W3C](https://www.w3.org/International/questions/qa-accept-lang-locales));
4. the instance default.

## Catalogs

Catalogs are JSON files, one per language, resolved in layers (top wins):

1. plugin catalogs (`<plugin>/locales/<lang>.json`);
2. the instance overlay (`<data dir>/locales/<lang>.json`, where the data dir is
   `~/.brambit` or `BRAMBIT_DATA_DIR`), so an operator can adjust wording without
   forking;
3. the core catalogs (`web/locales/<lang>.json`);
4. the same chain for the fallback languages, down to `en`;
5. the key itself.

Every layer may be partial.

## Keys

- Keys are **stable identifiers, never the sentence itself**: `confirm.delete_event.title`,
  not `"Delete this event?"`. Changing the English text must not invalidate the
  translations.
- Shape: `area.subject.detail`, lowercase `snake_case` segments. The first
  segment is the area (`confirm`, `routines`, `settings`, `errors`...).
- Name a key after its meaning, not its position on screen (`settings.save`, not
  `sidebar.button_3`).
- One key per meaning. Two places that happen to share the same English text but
  mean different things get two keys.
- When the meaning of a text changes, create a new key instead of editing the
  English text under the old one.

## Variables and plurals

- Variables use named placeholders: `"Couldn't rename it ({reason})"`. Never
  build a sentence by joining translated fragments; word order changes between
  languages.
- Plurals use the [CLDR](https://cldr.unicode.org/index/cldr-spec/plural-rules)
  categories as key suffixes, and the form is picked from `count` with the
  language's own rules (`Intl.PluralRules`), never with `count === 1` in code:

  ```json
  { "items_one": "{count} item", "items_other": "{count} items" }
  ```

  Languages with more forms add them (`_zero`, `_two`, `_few`, `_many`).

## Dates, numbers, money and time

These follow the person, not the server:

- format dates and numbers with `Intl` and the resolved language, never with a
  fixed locale such as `toLocaleString('pt-BR')`;
- show times in the person's time zone (`users.timezone`), never a fixed one;
- format money with `Intl.NumberFormat` and the currency of the amount.

## Plugins

A plugin ships its own `locales/<lang>.json` with keys under its own first
segment (the plugin name), so they never collide with the core. A plugin may
also ship a language the core does not have.

## Adding a language

1. Copy `web/locales/en.json` to `web/locales/<tag>.json` and translate the values.
2. Add the tag to the list of supported languages.
3. Run the checks below.

No code changes are needed.

## Checks

CI fails when:

- a catalog has a key that `en` does not have;
- a translation uses placeholders different from the `en` text;
- user-facing text is written directly in code instead of through a key.

A key missing from a non-English catalog is reported, not fatal; it falls back to
English.

## Migration

The core still carries mechanisms from before this design. They are keyed by the
Portuguese text and will be moved to the catalogs above one at a time, keeping
the Portuguese output identical:

- server messages (`web/mensagens-i18n.mjs`, `web/textos-servidor/`);
- confirmation cards (`web/confirm-textos.mjs`);
- app texts (`web/public/ui-texts.mjs`);
- routine texts (`web/public/routines.mjs`);
- site pages (`web/site-i18n.mjs`, `web/site-textos/`).

Until an area is migrated, keep its current key and add the translations, as
`AGENTS.md` says.
